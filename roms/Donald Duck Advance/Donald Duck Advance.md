Phase 0 header/trainer scan:

* Scanning the whole image for the 156-byte Nintendo logo gives **one** hit, at file `0x4`. There is no second/concatenated GBA header and no multi-game shell.
* The entry word is the stock branch; `0xB2` is `0x96`; the complement byte is correct. The 0xBE header-checksum word is zero, which is a common artifact of a rebuilt/cleaned header, not of a trainer (the entry point and first 4 KiB contain no cracktro).
* `strings` finds no `SUNHORS`, `CRC BANDIT`, `Mode7`, `trainer` or `crack` text. The final 4 KiB is all zero; the file ends exactly at the 8 MiB cartridge boundary. **No patch or trainer was found.**
* The `.sav` file written by mGBA remains 0 bytes through play, and the game's only continue path is a password screen. The title is password-based, not battery-backed.

## 2. Executive summary

The game's only developer-intended cheat surface is an **8-symbol password screen** reached through `CONTINUE`. It is not a table of hard-coded passwords: it is a **40-bit packed progress record + 4 check bits**, encoded as eight base-35 digits over a 35-symbol alphabet, XORed with `0xA93C67AAA1` and passed through a 40-bit permutation.

Recovered fields:

| Field | Width | Meaning (confidence) |
|---|---:|---|
| `a` | 7 bits, valid 0–99 | star count (`a<6` is clamped to 6 on apply) — **observed** |
| `b` | 3 bits, 0–7 | world/stage-group selector; the game's own generator caps it at 3 — **observed/inferred** |
| `c` | 5 bits, valid 0–16 | highest stage/level index reached — **derived** |
| `d` | 5 bits, valid 0..`c` | current stage/checkpoint index; used as bit index into `e` — **derived** |
| `e` | 16 bits | cleared/unlocked level bitfield; `0xFFFF` = all 16 levels — **observed** |
| checks | 4 bits | four XOR parities over field bits — **derived and exercised** |

Published code `2C1LTD!P` (GameFAQs, VGChartz, SuperCheats: "unlock all levels") does **not** occur literally in the ROM. It is generated by the ROM's own encoder for `(a=6, b=2, c=16, d=0, e=0xFFFF)`; the encoder reproduces it bit-for-bit, and the emulator accepts it.

The accessible published pages expose only that one password literal. A generated, unpublished code **`18JS5DHQ`** (`a=99, b=2, c=16, d=0, e=0xFFFF`) was typed on the real screen, accepted, and RAM-verified: the save record became `a=99`, `e=0xFFFF`, and the in-level HUD displayed **99** stars. A second unpublished string, **`W-J691!P`**, is an encoding alias of the published code (same decoded fields, different digits) and is also accepted. Bounds were proven by in-game rejection of `a=100`, `c=17`, `d>c`, `e >= 2^(c+2)`, a bad check bit, and an all-blank code.

No button-code system and no debug menu were found; the negative is bounded by a full menu walk, keyword/encoding scans, and key-mask table scans (see §6c).

## 3. How to reproduce

Emulator and display:

```bash
Xvfb :346 -screen 0 1024x768x24 &
DISPLAY=:346 openbox &
cd "roms/Donald Duck Advance"
DISPLAY=:346 SDL_AUDIODRIVER=dummy mgba -3 "Donald Duck Advance.gba"
```

mGBA 0.10.5 (SDL). Default SDL keymap used throughout: **A=`x`, B=`z`, L=`a`, R=`s`, Start=`Return`, Select=`BackSpace`, D-pad=arrows**. Hold keys ~120–150 ms; mGBA's SDL frontend ignores window-targeted `xdotool key --window`, so focus the window and send XTEST events.

Menu path:

1. Boot; wait through the Disney Interactive logo and title (about 8 s).
2. `Return` → main menu: `NEW GAME / CONTINUE / DEMO / OPTION / GALLERY / CREDITS`.
3. `Down` once to `CONTINUE`, `x` (A) → `INPUT PASSWORD`.
4. The entry screen shows 8 slots and a 35-cell keypad:
   * row 0: `- B C D F G H J K L M N` (indices 0–11)
   * row 1: `P Q R S T V W X Y Z 0` (indices 12–22)
   * row 2: `1 2 3 4 5 6 7 8 9 * ! #` (indices 23–34)
5. Move the cursor with the D-pad; `A` writes the highlighted symbol into the next slot and blanks the remaining slots; `Return` (Start) submits. `INVALID PASSWORD` is the rejection screen; a valid code goes to the level card.

Important transcription note: the large slot font draws **`G` (index 5) with a closed lower loop that looks like `6`**. The fresh-game code is **`G0ZWRX8W`**, not `60ZWRX8W`. The keypad's small-font `G` is unambiguous, and the ROM encoder reproduces `G0ZWRX8W` for the fresh save. Anyone transcribing the default screen as `60…` will get an invalid code.

Savestate/RAM method (used for repeatable tests): mGBA `.ss1` files are PNGs whose `gbAs` chunk is a zlib-compressed 397,312-byte state. Layout used here: state `0x0000` CPU/header, `0x1000–0x18FFF` VRAM, `0x19000–0x20FFF` IWRAM (`0x03000000` base), `0x21000–0x60FFF` EWRAM (`0x02000000` base). Decompress, patch, recompress with a correct PNG CRC, then load with `F1`. To force the password screen to redraw a patched digit buffer, press `Left` once (any D-pad press calls the redraw routine) before `Start`.

Patched test harness used:

1. Save a state at the fresh `INPUT PASSWORD` screen (`pwbase.ss1`).
2. For each code, restore that state, write the eight digits to `0x03005ED0` (as eight u32), load with `F1`, press `Left` to redraw, screenshot, press `Start`, screenshot.
3. For UI proof, the same code was also typed symbol-by-symbol with the BFS cursor planner described in §9.

## 5. Algorithm

### 5.1 Encode (ROM `0x08017F44`)

```
PERM[40] = {
 24, 8, 5,13, 7,15,33,34,23,31, 2,27, 0,37,39, 4,
 32,22, 6, 1,29,20,25,11,14, 3,38,26, 9,18,28,36,
 16,19,17,30,10,35,21,12
}
KEY = 0xA93C67AAA1            # low 32 bits 0x3C67AAA1, high byte 0xA9

# fields (already range-checked by the caller)
P  = a | (b << 7) | (c << 10) | (d << 15)
P |= (e & 0x0FFF) << 20
P |= (e >> 12) << 32
P |= ((a & 1) ^ ((c >> 1) & 1)) << 36
P |= ((b & 1) ^ ((e >> 1) & 1)) << 37
P |= ((d & 1) ^ ((a >> 1) & 1)) << 38
P |= ((c & 1) ^ ((b >> 1) & 1)) << 39

V = 0
for i in 0..39: V |= ((P >> i) & 1) << PERM[i]   # encoder: out[PERM[i]] = P[i]
D = V ^ KEY

low30 = D & 0x3FFFFFFF
high10 = (D >> 30) & 0x3FF
digits[0..5] = base35(low30)       # least significant first
digits[6..7] = base35(high10)
```

The eight digits are written to the buffer. The same function is used to prefill the password screen and to print the current password on the pause screen.

### 5.2 Decode / validate (ROM `0x0801809C`)

```
S1 = sum(digits[i] * 35**i for i in 0..5)
S2 = digits[6] + 35*digits[7]
D  = S1 | ((S2 & 3) << 30) | ((S2 >> 2) << 32)
V  = D ^ KEY

P = 0
for i in 0..39: P |= ((V >> PERM[i]) & 1) << i   # decoder: out[i] = V[PERM[i]]

a = P & 0x7F
b = (P >> 7) & 7
c = (P >> 10) & 0x1F
d = (P >> 15) & 0x1F
e = ((P >> 20) & 0xFFF) | (((P >> 32) & 0xF) << 12)

ok_checks =
    ((P >> 36) & 1) == ((a & 1) ^ ((c >> 1) & 1)) and
    ((P >> 37) & 1) == ((b & 1) ^ ((e >> 1) & 1)) and
    ((P >> 38) & 1) == ((d & 1) ^ ((a >> 1) & 1)) and
    ((P >> 39) & 1) == ((c & 1) ^ ((b >> 1) & 1))

range_ok = (a <= 99) and (b <= 7) and (c <= 16) and (d <= 16)
# e is 16 bits by construction; the ROM's 0xFFFF comparison always passes.
return ok_checks and range_ok
```

The decoder stores `{a,b,c,d,e}` at `0x03005EF0` and returns 1/0.

### 5.3 Semantic checks and save application (ROM `0x080161A8`)

After a valid decode:

```
if a > 99: reject
if a < 6: a = 6                 # 0..5 all become 6
if d > c: reject                # d+1 > c+1 comparison at 0x080161F2
if e >= (1 << (c + 2)): reject  # 0x08016208..0x08016212
save[0] = a
save[1] = d + 1
save[2] = c + 1
save[4] = e
save[8] = b
# then a display/apply helper 0x080129B4 decides final success
```

The `d <= c` and `e < 2^(c+2)` checks are why several checksum-valid, in-range codes are still rejected (see §6b). `0x080129B4` was not isolated further; it returns nonzero for all accepted cases tested.

### 5.4 Encoder's generator-side clamps (ROM `0x08016250`)

When the game builds a password from the current save, it clamps:

```
a = save[0]; if a < 6 then a = 6; if a > 99 then a = 99
b = save+8; if b > 3 then b = 3
c = save[2] - 1; if c > 16 then c = 16
d = save[1] - 1; if d > 16 then d = 16
e = save+4 (16 bits)
```

So the *generator* never emits `b > 3`, although the *validator* accepts `b` up to 7. This is the usual "generator narrower than validator" split.

## 6b. Enumeration

### 6b.1 Space definition

* Alphabet: 35 symbols (including `-`), length 8 → **35^8 = 2,251,875,390,625** raw digit strings.
* Packed value: **40 bits** → `2^40 = 1,099,511,627,776` encoded values.
* Payload: 36 bits (`a` 7 + `b` 3 + `c` 5 + `d` 5 + `e` 16), plus **4 check bits** computed from field parities.
* Canonical digit strings require the 6-digit low value `< 2^30` and the 2-digit high value `< 2^10`. Strings outside those ranges fold by OR and become **aliases** (see 6b.4).

Field-space count accepted by the validator + semantic layer:

```
sum over c=0..16, d=0..c, e=0..min(65535, 2^(c+2)-1),
         a=0..99, b=0..7
= 3,198,160,000 accepted field tuples
```

Because `a=0..5` is clamped to 6, the number of **distinct effects** is

```
sum ... a=6..99 ... = 3,006,270,400
```

Each accepted tuple maps to exactly one canonical 8-digit code; alias strings add further spellings of the same tuple (§6b.4). The accessible published pages expose **one** password literal (`2C1LTD!P`); GameFAQs' page reported "2 cheat codes and secrets" but returned 403, and its search snippet only exposes the password entry. No second password literal was recoverable, so at least 3,198,159,999 accepted field tuples (and their aliases) are unpublished.

### 6b.2 Published list verification

The only published password found is:

| Source | Code | Claim |
|---|---|---|
| GameFAQs (GBA/565777), VGChartz (14277), SuperCheats (934) | `2C1LTD!P` | unlock all levels |

Checks performed:

* Literal search for `2C1LTD!P` in the ROM: **0 hits** — the code is generated, not stored.
* ROM encoder on `(a=6,b=2,c=16,d=0,e=0xFFFF)` returns exactly `2C1LTD!P` and its digit vector `[24,2,23,9,16,3,33,12]`.
* The emulator accepts it and shows the level card.
* No other password appears on those pages; no code from a different platform/SKU was tested because the pages list none.

### 6b.3 Novel codes generated and confirmed in-game

1. **`18JS5DHQ`** — `(a=99, b=2, c=16, d=0, e=0xFFFF)`.
   * Typed symbol-by-symbol on the real `INPUT PASSWORD` screen (not RAM-injected): the screen showed `18JS5DHQ`.
   * `Start` → accepted, level card.
   * RAM: save record `a=0x63` (99), `e=0xFFFF`, `b=2`, `c=16`, `d=0`.
   * Effect: entering the level shows **99** in the star HUD.
   * This code appears in no published list.
2. **`W-J691!P`** — a different 8-symbol spelling of `(6,2,16,0,0xFFFF)` produced by adding `2^30` to the 6-digit low value. It decodes to the same fields and is accepted in-game (same level card). It is an unpublished alias of the published code, not a distinct effect.
3. **`K174HL2F`** — `(6,2,16,0,1)` accepted (a single level bit), showing that the bitfield is not fixed to `0xFFFF`.
4. **`4C1LTDQR`** — `(6,7,16,16,0xFFFF)` accepted and displays `MERLOCK'S TEMPLE 5`; `b=7` is outside the encoder's 0–3 range but inside the validator's 0–7 range.

### 6b.4 Aliasing (unused encoding freedom)

The decoder reconstructs the 40-bit value as

```
D = S1 | ((S2 & 3) << 30) | ((S2 >> 2) << 32)
```

where `S1` is the full 6-digit base-35 value (0..35^6-1 = 0..1,838,265,623). Canonical encodings have `S1 < 2^30`; when `S1` has bit 30 or 31 set, the OR forces those bits to 1 and loses the corresponding bits of `S2`, so several digit strings decode to the same `D`. `W-J691!P` demonstrates this: `S1` was increased by `2^30`, the string changed, the decoded fields did not. The ROM performs no overflow check in `0x0801809C`.

Consequence for enumeration: the count above is the number of **distinct decoded field tuples** (3,198,160,000). The number of accepted *strings* is larger by the alias multiplicity of each tuple. The multiplicity is at most **3**: `S1`'s bit 31 cannot be set because `2^31 = 2,147,483,648 > 35^6 = 1,838,265,624`, so only bit 30 of `S1` is free, and for a decoded bit 30 of 1 there are three `(S1 bit30, S2 low bit)` spellings that OR to the same value. No published list mentions aliases.

### 6b.5 Bounds proven by rejection

All tests used the real password screen; the rejection screen reads `INVALID PASSWORD`.

| Test | Field violation | Result |
|---|---|---|
| `5C60VDHQ` | `a=100 > 99` (checksum valid) | rejected |
| `53XLTD!P` | `c=17 > 16` (checksum valid) | rejected |
| `MPYD8TJX` | `c=2`, `e=16`; requires `e < 2^(c+2)=16` | rejected |
| `J1P5NJMW` | `c=2`, `d=3`; requires `d <= c` | rejected |
| `2C1LTD!N` | one check bit wrong; all fields in range | rejected |
| `----------` | all digits 0 | rejected |

This isolates three layers independently: the 4-bit check layer, the validator range layer, and the `0x080161A8` semantic layer.

### 6c.2 Button-code search

The shared input engine at `0x080038FC` stores only four words at `0x03003ED0`: current held, previous held, a repeat counter, and a handler pointer. It does **not** keep a press history. Any button code would therefore have to live in a per-screen handler comparing a sequence.

Static bounds:

* `strings -n 4` gives **57,439** strings.
* Keyword counts: `password` 2, `cheat` 0, `debug` 0, `secret` 0, `unlock` 0, `level select` 0, `sound test` 0, `gallery` 1, `option` 3. The same words are absent in UTF-16LE/BE and lowercase forms.
* `KEYINPUT` (`0x04000130`) is read at only two places: `0x08003900` (literal at `0x0800392C`) and `0x08003A8A` (literal at `0x08003A94`).
* A u16 scan for runs of ≥4 key-mask values (`1,2,4,8,0x10,0x20,0x40,0x80,0x100,0x200`) found 318 runs; only **15** contain ≥3 distinct masks, and **none** is referenced by a 32-bit ROM pointer. All 15 sit inside graphics/level data (offsets `0x32BBE`, `0x32BDC`, `0x1E0C20`, `0x1FC2A0`, `0x1FC2B4`, `0x200064`, `0x216D9C`, `0x216DB0`, `0x3FAE96`, `0x3FB152`, `0x45CF46`, `0x45DC6E`, `0x45EA72`, `0x4603F0`, `0x462688`) and are not tables used by input code.
* A byte scan found 1,359 short mask runs, but only 25 have a pointer to their start, and every one continues into non-mask bytes after 4–6 entries (graphics/code, not a terminated button sequence).

Conclusion: no developer button code or hidden debug menu is present in this image. The only input-driven cheat surface is the 8-symbol password screen.

## 7. Validation evidence

**Observed (emulator screens/RAM):**

* Main menu, OPTION, GALLERY, DEMO, CREDITS, password screen, level card, pause, and in-level HUD reached and screenshotted.
* `2C1LTD!P` accepted; `18JS5DHQ` typed and accepted; `W-J691!P`, `K174HL2F`, `4C1LTDQR`, `G0ZWRX8W` accepted.
* `5C60VDHQ`, `53XLTD!P`, `MPYD8TJX`, `J1P5NJMW`, `2C1LTD!N`, `----------` rejected with `INVALID PASSWORD`.
* Save RAM after `18JS5DHQ`: `63 01 11 00 ff ff 00 00 02 …` (a=99, e=0xFFFF, b=2, c=16, d=0).
* HUD after entering that level: **99** stars.
* Pause screen prints the live password; `4C1LTDNR` decoded to `(6,3,16,16,0xFFFF)` and the encoder reproduces `4C1LTDNR` from those fields.
* GALLERY with the all-levels save shows an unlocked illustration; fresh save shows 16 placeholder tiles.

**Derived (instruction-level):**

* Alphabet/cursor values come from the input handler storing the cursor index directly into the digit buffer.
* The 40-bit packing, XOR key, permutation, and four check equations are read from `0x0801809C` and confirmed by the encoder at `0x08017F44`.
* `a>99`, `d>c`, and `e >= 2^(c+2)` rejections are read from `0x080161A8` and confirmed by in-game rejection.
* `e` is a level-completion bitfield: `0x08016308` tests bit `(arg-1)` of save+4, and is called by level-card/level-state code at `0x0800DF94`, `0x0800E63C`, `0x0801333A`.
* Single code surface: BL/pointer xrefs show `0x0801809C` ← `0x080161B2` ← `0x0800D46C` only.

**Inferred (labelled):**

* `b` is a world/stage-group selector. Observed: `b=2,c=16` → `DUCKIE MOUNTAIN 1`; `b=7,c=16,d=16` → `MERLOCK'S TEMPLE 5`; `b=2,c=2` → `DUCKIE MOUNTAIN 3`. The game's generator caps `b` at 3, so `b=4..7` are validator-only values.
* `c` is the highest stage/level index and `d` the current one; `d` indexes the `e` bitfield. The exact card-title mapping for `c>=5` and `c=16` is not fully resolved (see §8).
* GALLERY images are gated by the same progress record; the bit→picture mapping was not enumerated.

## 8. Unknowns

* Exact `(b,c) → level name/number` mapping on the card. `c=2` shows level 3 and `c=16` shows level 1 for most `b`, while `b=7,c=16` shows `MERLOCK'S TEMPLE 5`. The card-title builder was not isolated; the field-level validator is fully proven regardless.
* Meaning of the `0` counter in the top-right of the in-level HUD and the 16-entry gallery bit mapping.
* Exact purpose/return condition of `0x080129B4` in the apply path; it returned nonzero for every accepted code tested, and its failure branch was not reached.
* Level-card arrow navigation: arrows produced no preview change in tests; whether they are decorative or require additional state was not proven.
* No debug menu was found; the negative is bounded by the scans in §6c, not by an exhaustive disassembly of every graphics routine.
