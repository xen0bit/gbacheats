## 2. Executive summary

The game has a genuine, developer-intended **10-character password system** on the title
menu (`ENTER PASSWORD`). The on-screen keyboard uses exactly 16 consonants
`B C D F G H J K / L M N P Q R S T` (alphabet string `bcdfghjklmnpqrst` at ROM
`0x08397D58`), i.e. 4 bits per character.

The password is **not a lookup table**: it is a checksummed 32-bit state word.
Characters 0–1 encode an 8-bit expected checksum; characters 2–9 encode a 32-bit payload
(8 nibbles) XOR-masked with a key derived from the checksum. The validator at
`0x08364EA8` calls the decoder/checker at `0x08376754`; on success it stores the decoded
32-bit payload at `0x03004BEC` and the screen displays **CORRECT PASSWORD**.

The complete space is characterised: 16¹⁰ = 1,099,511,627,776 strings, of which exactly
16⁸ = 4,294,967,296 are valid (one per 32-bit payload). A code that appears in no
published list was generated from the reversed encoder (`gqgghkgbhf`, payload all-zero)
and was accepted in the emulator with the in-game CORRECT PASSWORD message; a
bad-checksum code (`bbbbbbbbbb`) was rejected by the ROM's validator (return 0).

The game also contains an **unreachable developer menu label set**
(`2p duel test`, `2p dev test`, `credits` strings at `0x08377008`/`0x08377018`) and a
debug payload-display code path (`0x083661A6`, `0x08366578`), plus character-select
`-slots` (unlockable monsters). No reachable entry to the developer menu was found in
the enumerated menus (§8).

## 3. How to reproduce

**Emulator:** mGBA (SDL), Xvfb `:319`, `SDL_AUDIODRIVER=dummy`, keymap A=`x`, B=`z`,
Start=`Return`, Select=`BackSpace`, L=`a`, R=`s`, D-pad = arrow keys. Hold keys ~80 ms.

**Menu path to the password screen:**
1. Boot → title (`PRESS START`) → A → title menu.
2. Title menu entries (pointer table at file `0x376FC0`): `SINGLE PLAYER`,
   `2 PLAYERS`, `ENTER PASSWORD`, `CREDITS`.
3. Select `ENTER PASSWORD` (Down, Down, A).

**Keyboard:** 2 rows of 9 cells.
Row 1: `B C D F G H J K <backspace>`; Row 2: `L M N P Q R S T <OK>`.
Type 10 characters, move cursor to `OK`, press A. Max input length is **10** (the append
routine `0x08368400` clamps its length counter at `0x03000340`).

**Codes tested:**
- `gqgghkgbhf` — generated by `pw.py` from payload `[0,0,0,0,0,0,0,0]` → **accepted**
  (validator `r0=1`; screen shows `CORRECT PASSWORD`).
- `bbbbbbbbbb` — bad checksum (computed check `4`, required expected `0`) → **rejected**
  (validator `r0=0`; no CORRECT PASSWORD transition).
- `qhrsspmsnf` — generated from payload `[1,2,3,4,5,6,7,8]` → `r0=1` in GDB oracle.

Savestates `valid.ss1`, `valid2.ss1`, `invalid.ss1` in `/tmp/opencode/rampagepuzzle/`
contain these codes injected at the input buffer; loading them and pressing A on the
already-positioned `OK` cell reproduces the tests without retyping.

## 5. Algorithm

Reimplementation is in `/tmp/opencode/rampagepuzzle/pw.py`. Let `A = "bcdfghjklmnpqrst"`,
`idx(c)` = index of lowercased character in `A`; all arithmetic is on ints, masks as shown.

```
// prefix XOR: cumulative xor of 0..i-1 for i=0..7
XOR_PREFIX = [0, 0, 1, 3, 0, 4, 1, 7]

checksum(payload[0..7]) = (((sum(payload)+1) * 4549) ^ (sum(payload)+1)) & 0xFF

validate(pw[0..9]):
    if any char not in A: return reject
    expected = idx(pw[0]) + 16*idx(pw[1])            // 8-bit checksum from chars 0-1
    key = (expected * 17) & 15
    payload = []
    for i in 0..7:
        payload[i] = (idx(pw[2+i]) ^ key) & 15        // cumulative per-position mask
        key ^= i
    return accept iff expected == checksum(payload)

encode(payload[0..7]):                               // mint a code
    e = checksum(payload)
    pw[0] = A[e & 15];  pw[1] = A[(e >> 4) & 15]
    key = (e * 17) & 15
    for i in 0..7:
        pw[2+i] = A[(payload[i] ^ key) & 15]
        key ^= i
    return pw
```

Derivation notes (from disassembly, verified by GDB):
- `0x08376754` maps chars 0/1 to a byte via `idx0 + 16*idx1` (`0x083767A6`, `0x08367A4`).
- Each payload char is XORed with the running key `(expected*17) ^ cumulative_xor(i)`
  (`0x08367CE`, `0x08367F0`, `0x08367D2`, `0x0836828`); result masked with `&15`.
- The 8 nibbles are written LSB-first into an 8-byte scratch buffer (`0x08367FE`–`0x0836826`).
- The checker sums the 8 nibbles (`0x0836898`–`0x08368E0`) and computes
  `(((sum+1)*0x11C5) ^ (sum+1)) & 0xFF` (`0x0836918`–`0x0836922`), then compares to
  the expected byte (`0x0836926`).
- Success stores the first 4 scratch bytes (the 32-bit payload) at `0x03004BEC`
  (`0x08364EC0`–`0x08364EC6`).

## 6b. Enumeration

**Space definition.** 16 symbols × 10 positions ⇒ 16¹⁰ = **1,099,511,627,776**
submit-able strings. The decoder is a bijection for each fixed checksum byte, so every
32-bit payload has exactly one valid encoding. Valid codes = 16⁸ = **4,294,967,296**
(1 in 256 of all strings). Rejected = 255/256 of the space. No reserved/unused payload
bits were observed — all 32 bits reach the decoded word at `0x03004BEC`.

**Validator model.** `pw.py:decode()` and `pw.py:encode()` above; `decode()` was checked
against the ROM's own validator (`0x08364EA8`) through the GDB oracle: generated
`gqgghkgbhf` → `r0=1`, `qhrsspmsnf` → `r0=1`, `bbbbbbbbbb` → `r0=0`.

**Novel codes (absent from every published list — generated, not copied):**
| Code | Payload nibbles | Proof |
|---|---|---|
| `gqgghkgbhf` | all 0 | ROM validator `r0=1`; UI shows **CORRECT PASSWORD** (screenshot `valid_after.png`); decoded word at `0x03004BEC` = `0x00000000` |
| `qhrsspmsnf` | 1,2,3,4,5,6,7,8 | ROM validator `r0=1` (GDB oracle) |
| `blfchdhrfc` | 3,1,4,1,5,9,2,6 | `pw.py` round-trip valid (offline model) |

**Bounds proven by rejection.** `bbbbbbbbbb` has expected checksum 0 (idx('b')+16·idx('b'))
but the decoder over the 8 trailing `b` characters yields nibble sum 4 ⇒ computed
checksum `(((0+4+1)*4549) ^ (4+1)) & 0xFF = 4 ≠ 0`. The ROM's validator returned `r0=0`
and the game never produced CORRECT PASSWORD. This is an out-of-range/wrong-checksum
rejection, not an untested case. A truncated 9-character input was also rejected
(`r0=0`), confirming the length-10 requirement.

**Published-code verification.** Web search was unavailable in this environment
(`websearch` HTTP 503; GameFAQs 403; DuckDuckGo CAPTCHA; Bing returned unrelated
results; archive.org 404 for the cheats URL). No published code string was found in the
ROM, so none could be verified or contradicted. The ROM itself contains no
NUL-terminated 10-consonant preset password table (a scan of all 4 MiB found no
clustered candidate beyond compressed-data noise), which is consistent with an
algorithmic, table-less password system.

## 7. Validation evidence

**Observed**
- Title/menu/character/stage/password screens walked in mGBA (screenshots
  `menu*.png`, `cs*.png`, `next1.png`, `pw_screen.png`, `title.png`).
- Password keyboard is 16 consonants; input length clamps at 10.
- Patched savestate with `gqgghkgbhf` → A on OK → `CORRECT PASSWORD` (`valid_after.png`).
- Patched savestate with `bbbbbbbbbb` → A on OK → no success message; validator returns 0.
- GDB register dumps at `0x0836830C` (immediately after validator call): valid code
  `r0=1`, invalid code `r0=0`.
- GDB watchpoint on `0x0300035C`: A on OK flips the confirm flag (writer at `0x08367D30`).
- Decoded payload for all-zero code stored at `0x03004BEC = 0x00000000` (GDB,
  `gdb_payload.log`).

**Derived**
- Codec, checksum formula, XOR-key schedule, alphabet offsets and table addresses above
  — from disassembly of `0x08364EA8` and `0x08376754`, cross-checked against GDB oracle
  on three codes.
- Valid-code count 16⁸ from the bijection argument (per-checksum XOR masking is a
  permutation of the 16-symbol alphabet).

**Inferred (labelled)**
- The exact semantics of the 32 payload bits (which bits select mode/level/stage/
  character) were not isolated: after a successful password the game returns to the
  mode-select menu, and savestates taken before starting a subsequent game were
  byte-identical for two different payloads. The payload is definitely stored at
  `0x03004BEC`, but the consumer that maps it to mode/level was not identified.
- `2p duel test` / `2p dev test` are dead labels from the shipping build; the debug
  payload display at `0x083661A6`/`0x08366578` is real code but its trigger gate was
  not found.

No content found in fetched pages or ROM strings was treated as instructions.

## 8. Unknowns

1. **Payload field layout.** The 32-bit decoded word is stored at `0x03004BEC`, but no
   consumer mapping it to mode/level/stage/character was identified. Consequently the
   "novel combination" code uses an all-zero payload rather than a deliberately chosen
   level/character; its acceptance is still fully proven.
2. **Developer menu reachability.** Labels `2p duel test` / `2p dev test` / `credits`
   exist in a pointer pool (`0x08377008`–`0x08377038`) but no UI entry references them.
   Enumerated entry points: title menu (4 entries), mode select (4 entries), character
   select (9 slots incl. `?`), stage select. L+R and Select at the title were tested and
   revealed nothing. This is a bounded "no reachable dev menu on tested paths" result,
   not a claim about all possible button sequences.
3. **Unlockable `?` characters.** Character select shows a `?` placeholder (not
   selectable with A); unlock condition not determined.
4. **Web verification.** No published code list could be retrieved (all sources blocked
   as described in §6b), so "not in any published list" for the minted codes rests on the
   codes being algorithmically generated by a reversed encoder rather than transcribed.
5. **Two `AGBJ` multiboot images** at `0x3A8874`/`0x3A9E1C` were identified as link
   transfer payloads by header shape; their contents were not disassembled.
